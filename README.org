#+title: DaemonicCabal.jl

/Run a script many times, compile it once./

Each =julia script.jl= loads and compiles everything anew, then throws that work
away. =juliaclient= is a drop-in replacement for =julia= that runs your script in a
warm, long-lived Julia process (a /worker/) for your project, so only the first
run pays for loading and compiling.

* Getting started

Add the package and run ~DaemonicCabal.install()~ to set up the daemon and put
=juliaclient= on your path:

#+begin_src shell
julia --project=temp -e 'using Pkg; Pkg.add(url="https://github.com/tecosaur/DaemonicCabal.jl.git"); using DaemonicCabal; DaemonicCabal.install()'
#+end_src

Then use =juliaclient= wherever you would use =julia=:

#+begin_example
~$ juliaclient script.jl arg1 arg2
~$ juliaclient --project=. -e 'using MyPackage; MyPackage.main()'
~$ juliaclient  # a REPL
#+end_example

Most of =julia='s everyday switches carry over; =juliaclient --help= lists
them, along with the extras below. To see or change the daemon's settings, live
and in its service, run =juliaclient --reconfigure=.

DaemonicCabal runs on Linux (as a systemd user service), macOS (a launchd
agent), and Windows (a logon task), as well as FreeBSD and OpenBSD, where
=install()= prints the service setup for you to do by hand.

* How it works

#+begin_example
┌─────────────────┐      ┌──────────────────┐      ┌──────────────────────┐
│  Client (Zig)   │─────▶│  Conductor (Zig) │─────▶│  Worker Pool (Julia) │
└────────┬────────┘      └──────────────────┘      └────────┬─────────────┘
         │                                                  │
         └────────────────── stdio ─────────────────────────┘
#+end_example

=juliaclient= is a small Zig binary that asks the /conductor/, a Zig daemon,
for a worker, then talks to that worker directly. The conductor keeps one
worker per project, plus a spare already started, so even a project's first
run skips Julia's own startup.

When a worker's manifest or =dev='d package source changes on disk, the next
run gets a fresh worker.

* Live monitoring

To see what the daemon is up to, run =juliaclient --status=: it lists the
workers, the project each one serves, and their sessions and clients. With
=--status=live=, the list updates as things change, and you can select a
session to preview its output, see where it's stuck (even in a loop that never
yields), or interrupt or terminate it.

* Sessions

Each run normally starts with an empty =Main=, as it would in a new =julia=
process. =--session= keeps =Main= between runs from the same shell:

#+begin_example
~$ juliaclient --session -e 'x = 42'
~$ juliaclient --session -e 'println(x)'  # prints 42
#+end_example

Give the session a label, and any terminal can use it:

#+begin_example
# Terminal A
~$ juliaclient --session=shared -e 'data = [1,2,3]'

# Terminal B
~$ juliaclient --session=shared -e 'push!(data, 4); data'  # [1, 2, 3, 4]
#+end_example

A session keeps its worker when its code changes, with a warning; add =--revise=
to have Revise.jl pick up your edits.

** Sharing a REPL

=--sync= shares one REPL between terminals, much like =tmux=:

#+begin_example
# Terminal A: start a shared REPL
~$ juliaclient --sync --session=work

# Terminal B: attach to it
~$ juliaclient --sync --session=work

# Terminal C: run something in it, with the output shown in both REPLs
~$ juliaclient --sync --session=work -e 'x = 42'
#+end_example

Ctrl-D detaches just your terminal; the REPL ends once the last one leaves.

** Following a session

Sessions keep a transcript of their runs, which =--watch= shows from any
terminal: first what you missed, then the rest as it happens.

#+begin_example
# Terminal A: a long job
~$ juliaclient --session=job train.jl

# Terminal B: catch up, then follow along (Ctrl-C stops watching, not the job)
~$ juliaclient --session=job --watch

# Just the transcript so far, as JSON lines
~$ juliaclient --session=job --watch=json,once > job.jsonl
#+end_example

Sent to a file or pipe, the transcript shows each progress bar once, finished,
rather than as a thousand redraws.

* Sandboxing

On Linux, =--sandbox= runs your code in a user namespace (no root needed),
where it can only write to the project, or to the working directory outside a
project:

#+begin_example
~$ cd ~/myproject
~$ juliaclient --sandbox -e 'touch("ok")'           # works
~$ juliaclient --sandbox -e 'rm("/etc/passwd")'     # permission denied
#+end_example

The daemon can also serve other machines over TCP, sandboxing each remote
client in a worker of its own with a read-only depot, no view of your home
directory, and optional memory and CPU limits. Platforms other than Linux
refuse remote clients.

A client already in a sandbox of its own (bubblewrap, say) gets a worker started
inside it, so Julia sees the same filesystem the client does. The sandbox just
needs the daemon's runtime directory (where its sockets live) mounted.

* Memory usage

To avoid filling up system memory with idle workers, system memory usage is
monitored and idle workers reaped based to avoid being responsible for an OOM.
More actively and recently used workers are kept for longer, and the particular
behaviour is configurable.
